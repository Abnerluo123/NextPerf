# NextPerf —— 游戏性能计数器

> ### ⚠️ 这是一个早期版本，多项指标目前**不准或不可用**
>
> 注入链路、目录结构、**GPU 帧时间**已经实测可用；但 **CPU 帧时间、两个 Low 帧、
> RT Core 检测、Tensor / AI 检测都还没做好**，自动钩子与跨机器通用性**完全没测过**。
> 完整清单见下面的[已知问题与待改进](#已知问题与待改进必读)。**请不要把它当成成品工具。**


一个面向"调画质"场景的 Windows 性能计数器。除了 FPS / 占用率 / 温度 / 显存这些常规项，
它**想要**提供两个市面上大多数监控软件拿不到的指标：

* **RT Core 负载** —— 光追单元到底忙不忙 —— ❌ **目前未成功**
* **Tensor / AI 负载** —— 超分、帧生成这套 AI 管线吃掉了多少算力 —— ❌ **目前未成功**

以及 **CPU 帧时间与 GPU 帧时间分离**（GPU 那项已可用，CPU 那项不准）、
**帧生成时间实时曲线**、**1% / 0.1% Low**（Low 帧还不准）。

目标是在调画质时直接判断"降光追档位能换来多少帧"还是"瓶颈其实在 CPU"——
**但目前还做不到可靠判断，CPU 与 Low 帧两项数据不足以支撑这个结论。**

## 已知问题与待改进（必读）

下面这些是**已经确认存在**的问题，按「明确没有做好」如实列出，不做粉饰。

### 指标不准 / 不可用

| 指标 | 状态 | 说明 |
|---|---|---|
| **GPU 帧时间** | ✅ 可用 | 系统 PDH 按游戏进程读驱动累计 GPU 时间，与锁帧 / Reflex / 多线程提交无关 |
| **CPU 帧时间** | ❌ 不准 | 恒在帧周期附近（锁 60 时显示 ≈16.6 ms）。进程外无法区分 CPU 是「在算」还是「在等」，
| | | 所以现在这个值实际反映的是**帧周期**，不是 CPU 干的活 |
| **1% / 0.1% Low** | ❌ 不准 | 读数偏低（流畅的 60 fps 会显示 38~42）。数据源存在相位抖动，
| | | 正在从「钩子量 Present 间隔」切换到外置 ETW 内核事件 |
| **RT Core 负载** | ❌ 未成功 | 实机上测不到 DXR pass，多数时候显示「未检测到 DXR」 |
| **Tensor / AI 负载** | ❌ 未成功 | 多数时候显示「AI 已启用 · 估算中」，拿不到实测值 |

> **必须讲清楚**：RT Core / Tensor 这两项正是本项目的主要卖点，而它们目前**没做成**。
> WDDM 里没有独立的 RT 引擎，GeForce 上也没有公开的硬件计数器，所以只能靠「实测 DXR / compute
> 的 GPU 时间」去推算 —— 而这套插桩在真实游戏里还没打通。取不到时程序会显示「未检测到 DXR」，
> 而不是编一个数出来。

### 完全没有验证过的功能

* **自动钩子**（「添加游戏 exe」后进程一启动就自动注入）—— **未实测**
* **跨机器通用性** —— 只在下面那一台机器上跑过。**换机器 / 换显卡 / 换驱动，传感器很可能读不到数据**。
  代码里的数据源优先级（NVML → NVAPI → ADL → PDH → WMI → HWiNFO）没有在其它硬件上验证过
* Vulkan / OpenGL 游戏、独占全屏、多显示器、多显卡等场景覆盖有限
* 长时间运行的稳定性（连续玩几小时是否仍正常）未做系统验证

### 体验问题

* **UI 需要美化** —— 当前是「能用的工具界面」，不是「好看的界面」
* 高 DPI / 跨显示器拖动时窗口会裁切（`WM_DPICHANGED` 只重算布局，没按系统建议尺寸调整窗口）
* 点「注入到上一个游戏」时界面会卡住最长 10 秒（注入在 UI 线程里同步执行）

## 1. 快速开始

```
dist\NextPerf.exe
```

> **认准标题栏**：标题里带着构建时间戳，例如 `NextPerf  [2026-10-09 00:47]`。
> 如果标题只是光秃秃的 `NextPerf`，那说明你运行的是**别的副本**（不是这份源码构建的）——
> 磁盘上留了旧副本时特别容易发生，所有修复看起来都会"没生效"。
> 程序启动时还会无条件写一份 `%TEMP%\NextPerf.log`，有没有这个文件也是判据。

1. 打开后默认就开始监控，右上角会出现半透明参数面板。
2. 想看游戏内的数据（帧率、帧延迟、RT / Tensor 负载必须靠它），三条路任选：
   * **游戏已经在跑**：切到游戏窗口，再切回 NextPerf，点左侧 **注入到前台进程**
     —— 程序记住的是"上一个不是自己的前台窗口"，所以点按钮的那一刻前台是
     NextPerf 自己也没关系；
   * **想让它自动盯住**：**添加游戏 exe** → 选中游戏主程序，之后这个进程一启动
     就会被注入，不用每次手动点；
   * 注入成功后，主界面状态栏会写清用的是哪个进程、什么 API、多少 FPS。
3. 想改显示什么，直接勾左边的复选框，右上角面板和中间的预览会立刻跟着变。
4. 关掉主窗口不会退出，程序缩到系统托盘；托盘右键可以开始 / 停止 / 退出。

> **注入是能挂到"已经在跑的游戏"上的**（这是注入类工具最容易踩的坑）：
> 交换链在游戏启动时就建好了，光靠拦截 DXGI 的 `CreateSwapChain*` 永远等不到，
> 所以 NextPerf 会自己造一条临时交换链把 vtable 拿到手 —— 详见
> [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) 里「Present 是怎么挂上的」。

> **独占全屏**（不是无边框）的游戏里，Windows 会绕过桌面合成器，
> 任何独立窗口都盖不上去——这种情况必须注入（见"叠加是怎么画出来的"一节）。
> 注入成功后，面板是画在游戏画面里的，独占全屏同样能显示。

自检（不开窗口，跑一遍传感器和渲染，结果写 `selftest.txt`）：

```
dist\NextPerf.exe --selftest
```

## 2. 能显示哪些东西

| 分组 | 指标 |
| --- | --- |
| 帧率 / 帧时间 | FPS、帧生成时间(ms)、1% Low、0.1% Low、p99 / p99.9 帧时间 |
| 帧延迟 | **CPU 帧时间**（帧周期 − 卡在 Present 里等垂直同步的时间）、**GPU 帧时间**（GPU 时间戳实测，逐批求和，与锁帧无关） |
| 曲线 | 帧生成时间实时曲线；也可切成 FPS 或 CPU/GPU 双线 |
| CPU | 占用率、温度、频率、功耗、核心 / 线程数 |
| GPU | 占用率、温度、热点 / 显存结温、功耗（含上限）、核心 / 显存频率、风扇转速 |
| 显存 / 内存 | 显存已用 / 总量、内存已用 / 总量 |
| NVIDIA 利用率域 | 显存带宽占用（FB）、视频引擎（VID）、PCIe 总线（BUS）、**未公开域探测** |
| 光追 / AI | **RT Core 负载**、**Tensor / AI 负载**、已识别的 AI 模块（DLSS / FSR / XeSS / DirectML …） |
| 引擎 | 渲染 / 输出分辨率与缩放比、图形 API（D3D11 / D3D12 / Vulkan / OpenGL）、全屏模式、Draw / Dispatch 次数 |
| 诊断 | 当前生效的传感器数据源 |

### 关于 Low 帧

**1% Low** 的口径是：取最近窗口里**最慢的 1% 帧**，求它们的**平均帧时间**，再换算成 FPS。
（CapFrameX / OCAT 用的是同一种口径。）面板里另外也给出了 p99 / p99.9 的帧时间百分位方便对照。
直方图口徑不同的工具（比如直接取第 99 百分位帧时间）数值会略有差异，这是正常的。

## 3. RT Core 与 Tensor Core 负载是怎么测出来的

**先说结论：NVIDIA / AMD 都没有在 GeForce 驱动上公开"RT 单元占用率"和"Tensor 单元占用率"这两个硬件计数器。**
（NVAPI 公开的利用率域只有 4 个：图形引擎 GPU、显存控制器 FB、视频引擎 VID、PCIe 总线 BUS；
NVML 在 GeForce 上也不提供；DCGM 的 `PROF_TENSOR_ACTIVE` 只面向数据中心卡。）

所以任何号称"直接读硬件"的民用工具都不可信。NextPerf 的做法是**实测 + 推断**，并且把"是不是实测"标在数值后面：

### 3.1 RT Core —— 实测（DXR pass 的 GPU 时间占比）

注入游戏进程后，钩子会劫持 `ID3D12GraphicsCommandList4` 的

* `DispatchRays`（发起光线追踪）
* `BuildRaytracingAccelerationStructure`（构建 BVH）

在每一次调用的前后各插一条 **D3D12 TIMESTAMP 查询**，于是可以精确量出这一帧里所有光追 pass 花掉的 GPU 时间：

```
RT 负载 % = (本帧所有 RT pass 的 GPU 时间之和) / (本帧帧周期) × 100
```

分母用**帧周期**，含义是「光追 pass 吃掉了这一帧多少时间预算」。
绝对值（ms）也会一起显示，两个数都能自己核对。

> **不要**拿 GPU 帧时间当分母：那已经是「GPU 真正在干活的时间」，
> 光追占比拿它做分母会变成「光追占 GPU 工作的百分之多少」，口径完全不同。

分子分母都是 GPU 时间戳实测值，不是估算。DXR 只在 D3D12 上可用，因此 D3D11 游戏会显示"未检测到 DXR"。

### 3.2 Tensor / AI —— 实测优先，其次推断

AI 超分 / 帧生成（DLSS、FSR、XeSS、DirectML）普遍发生在"所有几何绘制之后"的 compute 阶段。
钩子会：

1. 检测进程里加载的 AI 模块（`nvngx_dlss.dll`、`nvngx_dlssg.dll`、`libxess.dll`、`DirectML.dll` …），面板上直接列出；
2. 劫持 `Dispatch`，用时间戳夹住"第一次发生在 draw 之后的 compute dispatch"到"最后一次"这段区间；
3. 用这段 GPU 时间除以本帧 GPU 总耗时，得到 **Tensor / AI 负载**。

如果某个游戏把 AI pass 和别的 compute 混在一起、或者只用 D3D11（拿不到时间戳），
面板会显示"AI 已启用 · 估算中"，告诉你这个数不可全信——**不会拿一个假数字糊弄你**。

### 3.3 硬件计数器：留了口子，一旦开放自动生效

程序同时在三个地方探测真正的硬件读数：

* **NVAPI 未公开利用率域 4..7**（`NVAPI_MAX_GPU_UTILIZATIONS = 8`，官方只用了前 4 个）。
  这些域一旦被厂商填上，面板会直接显示，来源标注"硬件"。
* **HWiNFO / LibreHardwareMonitor** 里若出现名字含 `Tensor` / `RT Core` 的读数，直接采用。
* **DCGM** 的 profiling 字段（数据中心卡）。

## 4. 叠加是怎么画出来的

两种模式，程序自动选（也能在"叠加模式"里强制指定）：

| 模式 | 原理 | 适用场景 |
| --- | --- | --- |
| **游戏内叠加** | 注入 `NextPerfHook.dll`，劫持 `IDXGISwapChain::Present`，在 Present 之前用游戏自己的设备把面板画到后台缓冲上 | 独占全屏、无边框、窗口化都行；**RT / Tensor 数据只有这条路能拿到** |
| **桌面叠加** | 一个 `WS_EX_LAYERED` 分层窗口，鼠标穿透，用 Direct2D 画好后 `UpdateLayeredWindow` | 无边框 / 窗口化；Vulkan、OpenGL 这种钩子暂时画不进去的场景兜底 |

**Present 是怎么挂上的**：交换链在游戏启动时就建好了，只拦截 DXGI 工厂的
`CreateSwapChain*` 是等不到的（那条路只在"进程刚起来就注入"时有效）。
所以注入后如果发现宿主已经在跑图形，程序会**自己造一条 8×8 的隐藏交换链**，
拿到 `IDXGISwapChain` 的 vtable 直接补丁 —— 同一个交换链类的 vtable 在 `dxgi.dll`
里是全进程共享的，所以游戏那条**已经存在的**交换链立刻就被接管了。
配置里的「注入探测交换链」可以关掉它（个别游戏对注入期创建设备敏感）。

两条路共用同一套 Direct2D + DirectWrite 绘制代码（先把面板渲染成一张 BGRA 位图），
所以**游戏内和桌面叠加长得一模一样**，主界面中间的预览也是同一套代码画的。

支持的图形 API：

| API | 帧计时 | 游戏内叠加 | RT / Tensor 实测 |
| --- | --- | --- | --- |
| DirectX 12 | ✅ | ✅ | ✅ |
| DirectX 11 | ✅ | ✅ | 仅 AI 模块识别（DXR 在 D3D11 上不存在） |
| Vulkan / OpenGL | ❌ | ❌（用桌面叠加显示传感器） | ❌ |

## 5. 传感器数据源与"自动优选"

程序会同时探测多个数据源，**每个指标独立选最优的那个**，UI 上会写明当前用了什么：

| 数据源 | 提供 | 说明 |
| --- | --- | --- |
| **NVML** | GPU 占用 / 温度 / 功耗 / 频率 / 风扇 / 显存 / 编码解码 | `nvml.dll` 动态加载，随 NVIDIA 驱动一起装 |
| **NVAPI** | 显存带宽占用、视频引擎、PCIe 总线、未公开域探测 | `nvapi64.dll` 动态加载。**部分新驱动版本会拒绝分发函数指针**，此时自动降级，不影响其它指标 |
| **AMD ADL** | GPU 占用 / 温度 / 频率 | `atiadlxx.dll` |
| **HWiNFO 共享内存** | CPU 温度 / 功耗、GPU 热点、显存结温、风扇 | 需在 HWiNFO 设置里打开 *Shared Memory Support* |
| **LibreHardwareMonitor** | 同上（WMI 接口） | 需在 LHM 里打开 WMI 远程访问 |
| **PDH 性能计数器** | 通用 GPU 引擎占用、显存占用、CPU 性能百分比 | 跨厂商兜底，任何 WDDM 2.x 显卡都能用 |
| **WMI** | ACPI 热区温度等 | CPU 温度的兜底来源 |

自动选择顺序：**厂商 SDK > 第三方监控软件共享内存 > PDH > WMI**。
多张显卡时会挑当前占用最高的那张（每 32 次轮询重新判断一次）。

## 7. 已知限制

* **Vulkan / OpenGL 游戏**：钩子不进入它们的渲染管线，只能用桌面叠加看传感器，帧率 / 帧延迟拿不到。
  这是当前实现的边界，不是设计选择——路线图里会补 Vulkan 的 `vkQueuePresentKHR` 时间戳。
* **反作弊**：带强反作弊的网游可能拒绝注入或把注入判定为作弊。请自行判断风险，**联机游戏请谨慎使用**。
* **注入需要"游戏已经起来"或"进程刚启动就被盯上"**：如果游戏在你的注入发生之前就已经
  跑起来、而且关闭了探测，那只能靠 `Present` 之外的信息（也就是只能看桌面叠加）。
  正常情况下两条路会自动选，不需要手动干预。
* **NVAPI 利用率域**：如第 5 节所说，部分驱动版本拿不到，会自动降级到 NVML / PDH。
* **CPU 温度**：Windows 上没有无驱动就能读到 CPU 温度的标准接口，
  没装 HWiNFO / LHM 时只能退到 ACPI 热区（很多主板不提供），会显示 `—`。
* **需要管理员权限的场景**：注入到以管理员身份运行的游戏时，NextPerf 也要以管理员身份启动。
  权限不够时状态栏会写「无法打开目标进程（可能需要管理员权限）」。

排查注入问题时看三个地方：

* **主界面「游戏进程」每行的右侧状态** —— 直接告诉你卡在哪一步：

  | 显示 | 含义 |
  | --- | --- |
  | `待注入` | 这个 exe 现在没在运行（还没启动，或者已经退出） |
  | `● 运行中 · 注入失败` | 进程在，但钩子没载进去 —— 看状态栏提示的具体原因 |
  | `● 已注入 · 未接管` | 钩子进去了，但没挂上 Present（多半是 Vulkan/OpenGL 游戏） |
  | `● 读取中` | 一切正常，数据在流 |

* **主界面底部状态栏** —— 注入失败的原因会在这里停 12 秒（不会再被刷新冲掉），
  包括 `打不开目标进程 —— 目标权限更高` 这种。这种情况点「以管理员身份重启」。
* **日志文件**（点界面上的「打开日志文件夹」即可）：

  | 文件 | 谁写的 | 什么时候有 |
  | --- | --- | --- |
  | `%TEMP%\NextPerf.log` | 主程序 | **总是有**。启动环境、游戏列表、每次注入尝试的每一步和错误码 |
  | `%TEMP%\NextPerfHook.log` | 注入进游戏的钩子 | 只有 DLL 真的载入之后才有 |

  两个文件都带 pid / tid，多进程共用。反馈问题时给这两份就够定位了。

命令行辅助（`tests/` 下）：

```
python tests\diag.py                       # 现场快照：DLL 依赖 / 正在跑什么 / 谁载入了钩子
python tests\try_inject.py Game.exe  # 对某个正在跑的进程做一次注入，逐步打印错误码
```

### 如果注入成功、但游戏出问题

NextPerf 往游戏进程里插了两类东西，可以**分开开关**来定位是哪一类引起的
（都在界面右侧「行为」区，改完立刻生效）：

| 现象 | 先试 | 说明 |
| --- | --- | --- |
| 游戏闪退 / 画面异常 | **叠加模式 → 强制桌面叠加** | 关掉「画进游戏后台缓冲」，保留帧率和 RT/Tensor 数据 |
| 游戏闪退 / 设备报错 | **深度引擎钩子 → 关闭** | 关掉往游戏命令列表插时间戳的那组钩子（Draw/Dispatch/DispatchRays） |
| 两个都关还是有问题 | 那就是 Present 计帧本身 | 把 `%TEMP%\NextPerfHook.log` 发我 |

钩子内部还有一层**自保**：D3D12 侧一旦发现命令列表 Reset/Close 失败，
会立刻永久停掉所有 D3D12 插入操作并写进日志，宁可不要数据也不把游戏搞崩。

另外注意：**Vulkan / OpenGL 游戏本来就拿不到帧数据**。
程序能识别出来，会显示「已注入 · Vulkan · 无帧数据」，并且**不会**在那种进程里
创建任何 D3D 设备（早期版本会，会把游戏带崩）。

## 8. 参考过的开源项目

写之前系统地看过这些项目，避免闭门造车：

* **Intel PresentMon** —— ETW 帧事件分析、GPU Busy 指标的定义方式
  （CapFrameX / OCAT / RTSS / PIX / NVIDIA FrameView 都构建在它之上）
* **LibreHardwareMonitor** —— Windows 传感器采集的事实标准
* **HWiNFO 共享内存** —— 复用成熟监控软件的读数，避免自己去写驱动
* **kiero / MinHook 一类的图形 API 钩子思路** —— vtable 劫持的常规做法
* **CapFrameX / OCAT** —— Low 帧与百分位的统计口径
